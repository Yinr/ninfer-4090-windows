# sm46-a3 — 为 RTX 4070 编译三元 Bonsai 引擎

本分支回答：**给 ninfer 的 sm_89 引擎加上 A3 调度补丁，到底能快多少？**

结论先行（全部在本卡实测，见下文）：

- **A3 有效：prefill 全区间 +6% ~ +10.7%，输出逐位不变。** 包方报的 +31.1% 是它自己的基线口径，本机约 10%。
- **E1（`-DNINFER_SM_COUNT=46`）无收益：重测为 +0.8%，落在 ±2% 噪声内。** 不采用，理由不是"它更慢"，而是"它没有收益，却要覆盖 per-arch 默认值并绑定具体显卡"。
- **部署用 `a3-default` 臂**（默认 SM=128 + A3），运行时 `set NINFER_TERNARY_TOKEN_GRID=1`。
- 本机存在一个 **2.2× 的双峰吞吐状态**（环境因素，非二进制因素）。§5 是本文件最重要的一节：
  任何顺序 A/B 测量在它面前都会得出错误结论。

## 分支内容

| 路径 | 说明 |
|---|---|
| `engine-sm89/` | 自包含引擎源码树（已内置三元算子，无需再打补丁） |
| `engine-sm89/ffmpeg/{include,lib}` | FFmpeg 头文件 + MSVC 导入库，**编译必需** |
| `patches-a3/` | A3 调度的 4 个**完整替换文件**（不是 diff） |
| `.github/workflows/build-sm46.yml` | 编译流水线 |

`engine-sm89/` 是随包提供的源码快照，与上游 fork 不同源，因此**本分支不通过 `git clone` 拉源码**，
而是把整棵树提交进来（已去掉 `ffmpeg/bin`、`ffmpeg/doc`、`tools/freq_corpus`、`.codex`，
31 MB）。编译所需的 FFmpeg 头文件与导入库保留；FFmpeg 运行时 DLL 不需要进仓库。

## 两个改造项

| 项 | 是什么 | 怎么生效 |
|---|---|---|
| **E1** | `-DNINFER_SM_COUNT=46`。`device.h` 里 `kTargetSmCount` 出厂默认 128（RTX 4090），被当作 `gridDim.y` 上界 `kTargetSmCount / KVHeads` 使用。**注意它是 `inline constexpr`，只能编译期定，没有任何运行时开关**。 | **编译期**宏 |
| **A3** | 三元 GEMM 的 token 轴铺进 `blockIdx.y`。prefill 时 T 很大但网格只铺了输出行轴 ⇒ 并行度上不去。 | **运行时** env `NINFER_TERNARY_TOKEN_GRID=1`（`0` 为对照臂） |

## 三个臂

| 臂 | 源码 | SM_COUNT | 运行时 | 用途 |
|---|---|---|---|---|
| `baseline` | 树原样 | 128 | — | 对照基线 |
| `sm46-a3` | 树 + A3 补丁 | 46 | `TOKEN_GRID=0` / `=1` | 历史臂；E1 与 A3 都烤在这一个二进制里 |
| **`a3-default`** | 树 + A3 补丁 | **0 = 不覆盖，取每架构默认（sm_89→128）** | `TOKEN_GRID=1` | **部署用这个** |

A3 是运行时 env，所以 `sm46-a3` 只需一个二进制就能分离 E1 和 A3；
`a3-default` 不传 `NINFER_SM_COUNT`，CMakeLists 会按架构解析成默认值
（`CMakeLists.txt:28-37`，sm_89→128 / sm_120→170），所以流水线的断言查的是**解析后的值**。

## 相对 `ternary-ci` 配方改动的地方

沿用 2026-09-25 跑通的配方（run `36092517775`，42m17s），三处改动都有原因：

1. **不再 `git clone` + `xcopy` 40 个补丁** —— 树已内置三元算子。
2. **不再预置 BtbN FFmpeg** —— 树内 `ffmpeg/{include,lib}` 已随包提供。
3. **去掉 `-DNINFER_ENABLE_AVX2` 与 `-DNINFER_CUDA_ARCH`** —— 这两个选项在当前 `CMakeLists.txt`
   里已不存在（`NINFER_TIER` 同样如此）。

## 门禁

- `CMAKE_CUDA_ARCHITECTURES` 只接受 `120a` / `120` / `89`，写错在 configure 阶段就 FATAL。
- `NINFER_SM_COUNT` 非数字直接 FATAL。
- configure 阶段 `message(STATUS ...)` 打印 `SM_COUNT`。
- 另有一步显式断言 `NINFER_SM_COUNT=<n>` 真的出现在 `build.ninja` 的编译行里
  ——旧 CI 踩过"宏没进编译行、编 40 分钟才发现白编"的坑。`sm_count=0` 时断言的是解析后的 128。
- 编译用 `-- -k 0`，一轮拿全所有编译错误。
- `apps/CMakeLists.txt` 无 `if()` 守卫，三个 exe（`ninfer` / `ninfer-serve` / `ninfer-perplexity`）
  在 `NINFER_BUILD_APPS=ON`（默认）下**同批产出** —— 这是数值门的前提，不要只重链 serve。
- 制品上传用 `if: always()`：制品是本 run 唯一不可再生的产物，不能被后续任何检查失败带走。

# 2. A3：有效，prefill +10%

### 2.1 基础 A/B

四臂，每题 3 次取中位数，开 `--no-prefix-reuse`（见 §6.2），ctx 32768 / fp8 / MTP K=3：

| 臂 | math | count | prose | **prefill** |
|---|---|---|---|---|
| factory（出厂二进制） | 47.4 | 118.4 | 57.6 | 1445 |
| baseline (SM=128) | 46.9 (−1.1%) | 118.2 (−0.2%) | 57.2 (−0.8%) | 1443 |
| sm46-a3 TG=0 | 47.0 (−0.8%) | 117.3 (−0.9%) | 56.8 (−1.4%) | **1432** |
| sm46-a3 **TG=1** | 46.9 (−1.1%) | 117.5 (−0.8%) | 57.1 (−0.9%) | **1580 (+10.3%)** |

**A3：prefill 1432 → 1580 = +10.3%**，decode 不变。第二轮独立复现 +10.06%（两轮差 < 0.5%）。
贪心输出四臂四题逐字一致。

### 2.2 prefill 长度扫描：A3 的收益来自哪里

三臂，每档 3 次取中位数，`--no-prefix-reuse`，ctx 32768 / fp8：

| 目标 tok | 实测 tok | baseline SM=128 | sm46 TG=0 | sm46 TG=1 | **A3 vs TG=0** |
|---|---|---|---|---|---|
| 256 | ~233 | 1209 | 1189 | 1261 | **+6.1%** |
| 512 | ~453 | 1406 | 1388 | 1511 | **+8.9%** |
| 1024 | ~857 | 1434 | 1419 | 1563 | **+10.1%** |
| 2048 | ~1630 | 1489 | 1472 | 1626 | **+10.5%** |
| 4096 | ~3212 | 1488 | 1474 | 1628 | **+10.4%** |
| 8192 | ~6402 | 1481 | 1472 | 1629 | **+10.7%** |
| 16384 | ~12759 | 1440 | 1425 | 1570 | **+10.2%** |
| 30000 | ~23300 | 1358 | 1352 | 1477 | **+9.2%** |

**A3 的收益是全区间稳定的**，不是长上下文专属：256 tok 就已经 +6.1%，23K 仍有 +9.2%——
符合它的机制，token 轴铺进 `gridIdx.y`，并行度提升与 T 的大小基本无关。

### 2.3 换二进制 / 换负载的交叉验证

为排除"收益只对某个二进制或某种负载成立"，固定 A3 开关，交叉两个二进制 × 两种负载
（`--no-prefix-reuse`，约 15K token）：

| 臂 | 负载A 重复文本 | 负载B 打乱语料 |
|---|---|---|
| factory | 1671 | 1585 |
| a3-default A3**关** | 1508 | 1439 |
| a3-default A3**开** | 1666 | 1581 |
| sm46 A3**关** | 1505 | 1438 |
| sm46 A3**开** | 1665 | 1581 |

A3 效应：SM=128 臂 +10.5% / +9.9%，SM=46 臂 +10.6% / +9.9%。**两个二进制、两种负载、五个格子全部吻合。**

# 3. E1：无收益（这一节推翻了本文件早期版本）

早期版本根据"8 档长度扫描里 E1 8 档全部慢 0.4~1.7%"判定 E1 是"真实的小回归而非噪声"。
**该结论不成立。** 两轮独立重测，都把 SM 数作为唯一变量：

| 测量 | 方法 | SM46 相对 SM128（都关 A3） |
|---|---|---|
| 交叉验证 | 顺序扫 5 臂，两种负载 | 负载A −0.2%，负载B −0.1% |
| E1 专门重测 | **ABBA 交替 8 个样本，全部同一吞吐档位** | **+0.8%** |

区间 −0.2% ~ +0.8%，全部落在噪声内。**E1 是中性的。**

原来那个"8 档一致变慢"是 §5 那个双峰状态造成的假象——档位在扫描中途切换，
方向一致的偏差只是漂移恰好落在一边。ABBA 重测的四臂结果：

| 对比 | 结果 |
|---|---|
| 重编·未打补丁·SM128 vs factory | −0.9% |
| 重编·打A3补丁·SM128·A3关 vs factory | −2.2% |
| **纯 E1：SM46 vs SM128**（仅 SM 数不同） | **+0.8%** |
| SM46 vs factory | −1.5% |

### 3.1 "重编二进制比出厂件慢 ~9%"——未解决，但不影响部署

这一项两轮测量互相矛盾，如实列出：

| 测量 | 方法 | 重编(A3关) 相对出厂 |
|---|---|---|
| 交叉验证 | 顺序扫 | 负载A **−9.8%**，负载B **−9.2%** |
| E1 专门重测 | ABBA 交替，全程单一档位 | **−0.9% / −2.2%** |

差了一倍。顺序扫那 −9% 有可能是双峰状态的假象（与 E1 那次同源），
但 ABBA 重测只覆盖到单一档位，**没有同时采到快慢两档**，所以无法证伪。
**结论：这个问题目前没有定论，不要引用 −9% 这个数字，也不要引用 −1% 这个数字。**

需要一次"出厂件 vs 重编(A3关)"的 ABBA 交替、并且跨到两个档位才能定论。

不过它**不影响部署决策**：部署件是"重编 + A3 开"，而这一组合对出厂件的优势
在 ABBA 同档位下是 **+8.6%（快档）/ +4.3%（慢档）**，两个档位方向一致。

所以不采用 E1 的理由是：

- 它没有可测收益；
- 它要覆盖 per-arch 默认值，并且与显卡强绑定，换卡就得重编 40 分钟 CI；
- 同一个二进制里它还与 A3 有害交互（见 §4）。

而不是"它更慢"。

# 4. 视觉

**必须常开。** 不带 `--vision` 时，任何带图请求都被拒绝：

```
POST /v1/chat/completions  ->  HTTP 400
INFO req#2 rejected during prepare | openai-chat non-stream | HTTP 400 | vision disabled | media 1
```

`--vision` **没有懒加载开关**——`--help` 原文是 "enables media and loads the fixed Vision
GPU allocations"，视觉的固定显存分配在启动时就建好了。所以视觉的代价无法按需付。

代价实测（**注意必须在正确的二进制上测**，见下）：

| 指标 | SM=128 部署件 | SM=46 臂 |
|---|---|---|
| prefill | −0.2% ~ +0.3%（**约等于零**） | **−11.1%** |
| decode | 约等于零 | −5.3% |
| 稳态显存 | +258 MiB | +258 MiB |

**"开视觉 prefill −11%" 这个数字只在 SM=46 臂上成立，在部署用的 SM=128 二进制上是零。**
这说明 E1 与 A3 存在有害交互：SM=46 把 `gridDim.y` 上界压到 `kTargetSmCount / KVHeads`，
A3 又要把 token 轴铺进 `grid.y`，两者叠加再叠加视觉路径（媒体 token 更多）就塌了。
**这是当初丢掉 E1 的一条独立且更有说服力的理由。**

包方包里唯一带视觉的启动器是 `start-8086.bat`，但它在 12 GB 卡上起不来：

```
FATAL server failed during startup | requested Engine runtime reservation
requires 9423359744 bytes, but only 4159878656 bytes are available
```

它要 ctx 262144 / fp8。可用的视觉组合是 **ctx 131072 + rk4v4 + `--vision`**，
本部署已把 `--vision` 并入 `start-8087-12g.bat`。

# 5. 测量陷阱：本机存在 2.2× 的双峰吞吐状态

**这是本文件最重要的一节。** 本机 prefill 吞吐会在两个状态之间跳变，**同一个二进制、
同样的请求、引擎配置完全一致**：

```
慢档  prefill 688 t/s   TTFT 20.6s   GPU 功耗 95 W
快档  prefill 1.53k t/s TTFT  9.2s   GPU 功耗 195 W
```

SM 频率（2760 MHz）与显存频率（10251 MHz）两档相同，温度 55–60 °C，风扇 30%，
`sw_power_cap` 采样到 `Active`。**功耗差一倍而频率相同 ⇒ GPU 在空等，不是在算。**

已逐项排除：

| 怀疑对象 | 结论 |
|---|---|
| 引擎配置 | 两档逐字一致（权重 7.39 GiB / KV 131,072 rk4v4 / pages 2048 / media 16 workers） |
| 主机侧 | 引擎自报 `host %` 两档都是 44–52% |
| 磁盘 | 关键文件全在 NVMe SSD；机械盘全程 0 MB/s |
| CPU | 1.9–6.0%，无争抢 |
| PCIe | Gen4 x16 满速 |
| 其它程序抢 GPU | 空闲时 GPU 利用率 1–2% |
| 温度 | 55–60 °C，远未过热 |

根因**尚未定位**（采集到 `sw_power_cap = Active`，机器装有 Armoury Crate 管理 GPU 档位，
但未证实）。它同样影响日常使用——落进慢档就等于 prefill 减半。

**因此本文件所有结论都必须遵守两条：**

1. **不要用顺序 A/B**。要 ABBA 交替（`A B B A A B B A`），让漂移对两臂对称。
2. **必须同档位比较**。把快档和慢档的数据混在一起比，会得出完全相反的结论。

本文件里被这个陷阱推翻过的结论，都已改正：E1 的"一致回归"（§3）。
A3 的净收益在 ABBA 同档位重测下是 **+8.6%（快档）/ +4.3%（慢档）**，两个档位方向一致。
唯一仍未解决的是 §3.1 那个"重编 vs 出厂"的 −9% / −1% 分歧。

# 6. 其它两个测量坑

### 6.1 `ninfer-perplexity` 在 context ≥ 984 时必崩（上游引擎 bug）

任何 `--context ≥ 984` 的 perplexity 运行在第一个窗口抛
`error: scoring ... window 0 failed: bad allocation`。与语料长度和 context 无关，
**只与窗口实际 token 数有关**（≥984 挂，≤983 过）。

根因：`causal_score` 的 workspace 计划只按三个 flush 张量定容，漏算了输出头
`ops::linear` 的三元 workspace；同时 `ternary_dispatch()` 在 `folded_activation()`
已申请之后又申请了一次 int8 的 `codes`/`scales`。

- 抛出点：`src/core/arena.cu:462`
- 计划：`src/targets/qwen3_6/impl/runtime/layouts_impl.h:413-420`（`kCausalScoreTile = 1024`）
- 双算：`src/ops/linear/ternary/ternary_dispatch.cpp:98-99`

T=1024 需要 524,300,800 B，计划只有 508,567,552 B，差 15,733,248 B；实测边界
**T=983 过 / T=984 挂**，证实是双算。没有开关可绕，数值门因此用 `--context 768`。

### 6.2 前缀复用：命中快 124 倍，未命中慢 2.1 倍

`--no-prefix-reuse` 关掉前缀复用。测它值不值，因为聊天客户端每轮都重发同一段前缀：

| | 缓存命中（同提示连发） | 缓存未命中（每次全新提示） |
|---|---|---|
| 复用 ON | 13,837 → **只算 7 token，195,892 t/s** | 678–767 t/s |
| 复用 OFF | 全量重算 1,584 t/s | 1,551–1,580 t/s |

未命中时复用的净代价随长度增长：**−27.1% / −52.6% / −67.7%**
（复用 × A3 的 2×2 实测，实际 token 数 3436 / 13725 / 30754；A3 开关在四格里只贡献 +2% 左右，
说明 §6.2 最后那条"测 prefill 必须加 `--no-prefix-reuse`"的警告同样适用于 A3 本身）。

**结论：保持默认开启。** 命中时快 124 倍，未命中时慢 2.1 倍；聊天/agent 负载命中率高，
默认值是对的。但要知道这个代价，并在测 prefill 时必须加 `--no-prefix-reuse`
——否则测到的是"小 T 预填充"而不是长上下文预填充（nonce 放在提示开头、其余文字完全相同，
缓存命中后只剩几十个 token 要算，会把 A3 的收益测成 +1.3%）。

### 6.3 两个脚本坑

- **`timings.prompt_n` 不是 prompt 总长**，是"实际预填充的 token 数"。前缀缓存命中后从 35 掉到 7，
  各臂不可比。应该用 `usage.prompt_tokens`。
- **PowerShell 变量大小写不敏感**：`$q` 就是 `$Q`。题组用 `$Q`、prefill 的 nonce 也叫 `$q`，
  第一个臂跑完后 `$Q` 被覆盖成字符串，后续各臂 `foreach ($k in $Q.Keys)` 一次都不执行，
  表现为莫名其妙的 `prompt_n=12` 和全线 37 t/s。
- `Kill-Port` 只按端口杀进程，而 `ninfer-serve` 会残留并继续占显存。
  现在每臂开跑前杀掉全部 ninfer 进程并等显存回落到 1500 MiB 以下。

### 6.4 显存要在稳定后采样

引擎绑定端口后还在继续分配 KV。**在监听瞬间采样会低报约 2.9 GiB**：
同一配置下监听瞬间读到 8,497 MiB，稳定后是 **11,388 MiB**（占 12282 MiB 的 93%，
余量约 894 MiB）。低功耗档采样还可能落在双峰的另一侧。
